# CATalyst ML — Synthetic Datasets

Generated by `generate_dataset.py`. All output lives in `ml/data/`.
Date range: **2023-01-01 → 2025-12-31** (1096 days).
Seeded (`random.seed(42)`) — regenerate any time and get identical output.

## Run

```bash
cd ml
python generate_dataset.py
```

No dependencies beyond the Python stdlib (only `pandas` is needed for the sanity checks). Takes ~30-60 seconds and writes 8 CSVs (~200 MB total, dominated by `usage_logs.csv`).

## Files

| File | Rows | Purpose |
| --- | --- | --- |
| `equipment.csv` | 220 | Fleet master — type, manufacturer, model, expected engine/idle/fuel baselines |
| `sites.csv` | 30 | Site master with `region` (for weather join) and `geofence_radius_m` |
| `operators.csv` | 60 | Operator master |
| `customers.csv` | 45 | Customer master with `segment` and bulk/contract probabilities |
| `weather.csv` | 5,480 | Daily weather per region (5 regions × 1096 days) |
| `rentals.csv` | ~52K | Historical rentals, one row per equipment unit |
| `usage_logs.csv` | ~1.27M | Per-day per-rental telemetry — **anomaly detection training source** |
| `demand_daily.csv` | ~60K | Aggregated demand per (date, region, equipment_type) — **forecasting target** |

## Field guide

### `rentals.csv`
`rental_id, equipment_id, equipment_type, site_id, region, customer_id, customer_segment, operator_id, rental_start_date, expected_return_date, actual_return_date, rental_days, quantity, contract_id, is_bulk_order, has_contract, rental_status, overdue_days`

- `is_bulk_order` — **label**. `1` = large planned order from mining_corp / gov_infra with a `contract_id`. Feed this to forecasting as a feature; anomaly detection should NOT see raw order volume — only per-asset behavior.
- `overdue_days` — 0 for on-time, >0 for late returns (~4% of rentals).

### `usage_logs.csv`
`log_id, log_date, rental_id, equipment_id, equipment_type, site_id, region, operator_id, engine_hours, idle_hours, fuel_consumed_liters, expected_fuel_liters, utilization_rate, gps_ping_count, last_ping_gap_hours, latitude, longitude, inside_geofence, overdue_flag, is_bulk_order, customer_segment, has_contract, is_anomaly, anomaly_type`

- `is_anomaly` / `anomaly_type` — **labels**. Types injected: `idle_spike`, `fuel_mismatch`, `gps_loss`, `unauth_operator`, `geofence_breach`, `overdue_usage`, `none`.
- `utilization_rate = engine_hours / (engine_hours + idle_hours)` — strong feature.
- `expected_fuel_liters` — physics-based baseline (`engine_hours × fuel_rate`). Compare against `fuel_consumed_liters` to spot theft/waste.

### `demand_daily.csv`
`date, region, equipment_type, units_active, new_bookings, bulk_units, month, day_of_week, day_of_year, season, is_weekend`

- Target for forecasting: **`new_bookings`** (leading indicator) or **`units_active`** (fleet-level demand).
- `bulk_units` — how many of the day's active units came from bulk contracts. Useful as a separate exogenous feature so the model can model "planned" vs "organic" demand separately.
- Every (date, region, equipment_type) combination is present — including zero-demand rows — so the series is continuous.

### `weather.csv`
`date, region, temp_c, precipitation_mm, snowfall_mm, season`

Join to `demand_daily.csv` on `(date, region)` to give the forecast model temperature/snow features.

## Baked-in signals

### Seasonality (built into `SEASONALITY` table in the generator)
- **Snow_Remover** — heavy Nov–Feb (>2× baseline), near-zero Jun–Aug.
- **Excavator / Bulldozer / Grader / Concrete_Mixer / Compactor** — construction peak Apr–Oct, dip in winter.
- **Generator** — peaks Jun–Sep (summer heat + storm season).
- **Loader / Dump_Truck / Drill_Rig** — near-flat (mining runs year-round).

### Bulk-order handling — the "Caterpillar mining order" case
- `mining_corp` and `gov_infra` customers roll bulk orders with high probability. Each bulk order books 8–30 units of the same type across a shared `contract_id` and runs 20–60 days.
- Every bulk rental has `is_bulk_order=1` and a non-empty `contract_id`. **Sanity-check confirmed:** anomaly rate is 5.6% for bulk vs 6.6% for non-bulk — statistically identical, so bulk-order size does NOT leak into the anomaly label.

### Injected anomalies (~5% of usage days, plus overdue rollup → 6.16% total)
| type | signal | how to detect |
| --- | --- | --- |
| `idle_spike` | idle_hours 19–24, engine near 0 | idle_hours or `1-utilization_rate` |
| `fuel_mismatch` | fuel_consumed ∈ [0.1×, 4×] expected | \|fuel_consumed / expected_fuel - 1\| |
| `gps_loss` | ping_count=0, gap 24–72h | `gps_ping_count`, `last_ping_gap_hours` |
| `unauth_operator` | operator_id empty on active rental | `operator_id == ""` |
| `geofence_breach` | lat/lon 5–20 km off site | `inside_geofence == 0` |
| `overdue_usage` | log_date > expected_return | `overdue_flag == 1` |

## Suggested models (for the 24-hr build)

**Demand forecasting** — target `new_bookings` (or `units_active`) per (region, equipment_type):
1. Baseline — linear regression on `[month, day_of_week, day_of_year, season, is_weekend, temp_c, snowfall_mm, precipitation_mm]`.
2. Better — Gradient Boosted Trees (`sklearn.ensemble.GradientBoostingRegressor` or `xgboost`) — handles seasonality × weather interactions.
3. Time-aware — `Prophet` (facebook/prophet) if you want built-in trend+seasonality with almost no tuning.
4. Deep — `sktime` or a simple LSTM if you have GPU time — likely overkill for 24 hrs.

**Anomaly detection** — per-day usage row:
1. Baseline — `IsolationForest` on `[engine_hours, idle_hours, utilization_rate, fuel_consumed_liters, fuel_ratio, gps_ping_count, last_ping_gap_hours, inside_geofence, overdue_flag]`. Unsupervised, fast.
2. Supervised — `RandomForestClassifier` with `is_anomaly` as label + `anomaly_type` for multi-class. Class-weight balanced.
3. Rule + ML hybrid — hard rules for the physics-derivable ones (`inside_geofence==0`, `operator_id==""`, `fuel_ratio > 2.5`) + Isolation Forest for the fuzzy behavioral patterns. Best explainability for demo.

**Explicit rule for both models: do NOT feed anomaly detection the `is_bulk_order` / `customer_segment` / `quantity` fields.** Those belong to forecasting. Keeping the two feature-sets disjoint is what prevents "bulk = spam" false positives.

## Regenerating with different scale

Tweak the top of `generate_dataset.py`:
- `START_DATE` / `END_DATE` — length of history
- `build_equipment(target_units=...)` — fleet size
- `build_sites(target_sites=...)` — number of sites
- Base bookings/day is driven by `expected = 0.6 * season_mult` inside `build_rentals_and_logs`
